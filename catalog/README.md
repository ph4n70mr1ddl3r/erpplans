# Workflow Catalog — Machine-Readable Projection

A queryable JSON projection of the workflow corpus, generated by
[`../07-methodology/generate-catalog.py`](../07-methodology/generate-catalog.py)
from the same parse that drives the BPMN tree. The markdown under
`01-model-company/workflows/` remains the **single source of truth** — this
tree is a derived artifact exactly like [`../bpmn/`](../bpmn/README.md) and
[`../dmn/`](../dmn/README.md): regenerate via
`python3 07-methodology/generate-catalog.py`, never hand-edit.

**Guarded:** `validate-repo.sh` Check 71 invokes the generator's `--check`
mode every run — the shipped JSON must be byte-identical to the in-memory
regeneration, and the Quick-Stats table below is pinned to the regenerated
counts. A markdown edit without catalog regeneration fails validation, and a
hand-edited JSON file fails it too (the seventeenth-wave content-mirror
doctrine, one projection further).

## Per-PA schema (`erpplans-catalog/1.0`)

| Key | Meaning |
|---|---|
| `schema`, `source` | projection version; the PA markdown this file mirrors |
| `value_stream` | `id` (VS-n), human `name` (from the VS README H1), `directory` |
| `process_area` | `id` (PA-n.n) and `title` (from the PA H1) |
| `workflows[]` | one record per `##`/`###`/`####` W-header in the PA |

Per-workflow record:

| Key | Meaning |
|---|---|
| `id`, `name` | workflow id (W24, W7C, …) and title |
| `level` | 2 = primary `##`, 3/4 = sub-workflow |
| `tier` | confirmed tier re-derived from the criticality register (all 5,450 resolve; register foots 1,396 + 3,296 + 758) |
| `parent` | nearest preceding primary in the same PA (null for primaries) — sub-workflows hang off their umbrella (`### W22A` → `W22`) |
| `fields` | the `\| **Label** \| value \|` table rows (Trigger, Frequency, Volume, Owner, Participants, …), markdown stripped |
| `steps` | rows from canonical 5-column steps tables (header `\| # \| Activity \| Role (R) \| Role (A) \| Duration/Frequency/Latency \|`) |
| `sections` | every `###` section under the workflow, verbatim bullet lines, keyed by heading |
| `ctl_refs` | every `CTL-n` token in the workflow's text |
| `w_refs` | every other `W-n` token (cross-reference impact analysis) |
| `req_refs` | requirement-ID tokens, filtered to the 728 defined `erp-requirements.md` IDs (over-capture guard) |

## Projection notes

- **Step rows exceed the BPMN task count** (23,099 here vs 23,016
  `<bpmn:task>` elements): the BPMN emitter requires bare-numeric step ids and
  silently skips prefixed forms (`CS-1`… in W525's sync tables, and siblings).
  The catalog keeps every row — the id form is preserved verbatim in `n`.
- **Family-level presence**: some umbrellas (`## W2`, `## W5`, `## W12`,
  `## W9`) hold no content of their own — their fields/steps/sections live in
  their `###` children — and some primaries share sections with a child
  (`## W22` / `### W22A`). The generator validates presence over the
  primary + children union, mirroring the corpus's own convention; per-record
  JSON stays faithful to what each block actually holds.
- **Suffixed variant sections** (`System Touchpoints (W596 — …)`,
  `Time Estimate (W22A)`) are kept under their literal headings and count as
  present via prefix match.
- Serialization is deterministic (`sort_keys`, trailing newline) so `--check`
  byte-comparison is stable across runs.
